# KnowFlow

KnowFlow is a workspace-based business knowledge platform. Its approved product and technical scope is documented in the [Project Blueprint](docs/KnowFlow_Project_Blueprint.pdf), the [V1 Detailed Design](docs/KnowFlow_V1_Detailed_Design.pdf), and the editable [design source](docs/knowflow-v1-design.md). Architecture decisions are recorded in [docs/adr](docs/adr/).

## Current milestone

M1 Foundation, M2 Identity & Tenancy, and M3 Knowledge Areas & Documents are implemented. M3 adds workspace-scoped areas, private PDF upload and storage, document metadata, authorized viewing/download, and deletion with a retained cleanup tombstone. Text extraction, processing jobs, search, and answers remain later milestones.

## Requirements

- Docker Engine with Docker Compose v2
- Node.js 22.13 or newer and npm (for frontend work outside Docker)
- Python 3.12 (for backend work outside Docker)

## Configure WorkOS AuthKit

Create a WorkOS staging environment, then copy `.env.example` and set:

- `WORKOS_CLIENT_ID` and `WORKOS_API_KEY` from the WorkOS dashboard.
- `WORKOS_COOKIE_PASSWORD` to a private value generated by `openssl rand -base64 32`.
- `NEXT_PUBLIC_WORKOS_REDIRECT_URI` to `http://localhost:3000/callback`.
- `WORKOS_ISSUER` only if the environment uses a custom issuer; otherwise leave it empty.

In the WorkOS application settings, allow `http://localhost:3000/callback` as a redirect URI, set `http://localhost:3000/sign-in` as the initiate-login URI, and set `http://localhost:3000/` as the sign-out redirect URI. Use verified WorkOS accounts. WorkOS identifies the person; workspace roles and data access come only from KnowFlow's PostgreSQL memberships.

AuthKit access tokens do not include an `aud` claim by default. In the WorkOS JWT Templates settings, add the API audience as a custom claim using the exact value configured in `WORKOS_TOKEN_AUDIENCE` (the local default is `https://api.knowflow.example`):

```json
{"aud":"https://api.knowflow.example"}
```

FastAPI requires that exact audience along with a valid WorkOS signature, issuer, expiry and subject. If the WorkOS environment uses a non-default issuer, set `WORKOS_ISSUER` to the exact issuer from a token. This is necessary for the approved API-token validation flow; it does not change the workspace authorization model.

The browser receives only the sealed HttpOnly AuthKit cookie. Next.js server components and actions forward short-lived access tokens to FastAPI; browser JavaScript does not receive those tokens.

## Start the local application

```sh
cp .env.example .env
docker compose up --build -d
docker compose run --rm api alembic upgrade head
```

The local services are:

- KnowFlow sign-in and workspace UI: <http://localhost:3000>
- FastAPI and OpenAPI: <http://localhost:8000/docs>
- API liveness/readiness: <http://localhost:8000/health/live> and <http://localhost:8000/health/ready>
- Identity API: `GET /api/v1/me`
- Workspace API: `GET/POST /api/v1/workspaces`, `GET /api/v1/workspaces/{id}`, and workspace member endpoints.
- Knowledge areas: `GET/POST /api/v1/workspaces/{id}/knowledge-areas`, `GET/PATCH/DELETE /api/v1/workspaces/{id}/knowledge-areas/{area_id}`. Members can read; Owners manage.
- Documents: `GET/POST /api/v1/workspaces/{id}/documents`, `GET/DELETE /api/v1/workspaces/{id}/documents/{document_id}`, and `GET /api/v1/workspaces/{id}/documents/{document_id}/content`. Owners upload/delete; Members can view/download. Originals are private MinIO objects locally; PostgreSQL stores metadata.
- PostgreSQL with pgvector: `localhost:5432`
- MinIO console: <http://localhost:9001>

M3 accepts PDF files with a valid PDF structure, no password protection, up to 20 MiB and 250 pages. Processing status remains `UPLOADED` in M3; extraction, text-based/scanned content checks, and downstream processing are M4 work. A deleted document immediately returns 404 to application requests. Storage cleanup is retried on an Owner delete request for up to 24 hours; after successful cleanup, the metadata tombstone remains for 7 days and is then purged during subsequent document/area operations.

Readiness is expected to fail until the database migrations have been applied. Copy `.env.example` to `.env`, configure WorkOS, then start Compose. The example database and object-store credentials are local development defaults only.

## Run checks

```sh
docker compose run --rm api ruff check app tests migrations
docker compose run --rm api pytest
docker compose run --rm web npm run lint
docker compose run --rm web npm run typecheck
docker compose run --rm web npm run build
```

## Stop local services

```sh
docker compose down
```

Remove the local database and object storage volumes only when you intend to discard local data:

```sh
docker compose down --volumes
```

Do not commit `.env` or provider secrets. Authentication works only after WorkOS staging credentials and redirect settings are configured.
