# KnowFlow

KnowFlow is a workspace-based business knowledge platform. Its approved product and technical scope is documented in the [Project Blueprint](docs/KnowFlow_Project_Blueprint.pdf), the [V1 Detailed Design](docs/KnowFlow_V1_Detailed_Design.pdf), and the editable [design source](docs/knowflow-v1-design.md). Architecture decisions are recorded in [docs/adr](docs/adr/).

## Current milestone

M1–M7 are approved and frozen. M8.1 proved the deployment ONNX E5 runtime under a 512 MiB container limit; M8.2 prepares an opt-in combined API/worker backend topology. Deployment itself, Neon provisioning, and M8.3 have not started.

## Requirements

- Docker Engine with Docker Compose v2
- Node.js 22.13 or newer and npm (for frontend work outside Docker)
- Python 3.12 (for backend work outside Docker)

## Configure WorkOS AuthKit

Create a WorkOS staging environment, then copy `.env.example` and set:

- `WORKOS_CLIENT_ID` and `WORKOS_API_KEY` from the WorkOS dashboard.
- `WORKOS_COOKIE_PASSWORD` to a private value generated by `openssl rand -base64 32`.
- `NEXT_PUBLIC_WORKOS_REDIRECT_URI` to `http://localhost:3000/callback`.
- `WORKOS_ISSUER` only if the environment uses a custom issuer; otherwise leave it empty.

In the WorkOS application settings, allow `http://localhost:3000/callback` as a redirect URI, set `http://localhost:3000/sign-in` as the initiate-login URI, and set `http://localhost:3000/` as the sign-out redirect URI. Use verified WorkOS accounts. WorkOS identifies the person; workspace roles and data access come only from KnowFlow's PostgreSQL memberships.

AuthKit access tokens do not include an `aud` claim by default. In the WorkOS JWT Templates settings, add the API audience as a custom claim using the exact value configured in `WORKOS_TOKEN_AUDIENCE` (the local default is `https://api.knowflow.example`):

```json
{"aud":"https://api.knowflow.example"}
```

FastAPI requires that exact audience along with a valid WorkOS signature, issuer, expiry and subject. If the WorkOS environment uses a non-default issuer, set `WORKOS_ISSUER` to the exact issuer from a token. This is necessary for the approved API-token validation flow; it does not change the workspace authorization model.

The browser receives only the sealed HttpOnly AuthKit cookie. Next.js server components and actions forward short-lived access tokens to FastAPI; browser JavaScript does not receive those tokens.

## Start the local application

```sh
cp .env.example .env
docker compose up --build -d
docker compose run --rm api alembic upgrade head
```

The worker downloads the pretrained embedding model from Hugging Face on its first startup into the persistent `model_cache` Docker volume (approximately 133 MB). Internet is needed for this first download only. After a successful model load, a cache marker makes API/worker loads use local files only; subsequent `docker compose down` / `up` cycles reuse the model without internet. An interrupted download is retried online and does not create the marker. `docker compose down --volumes` removes the cache along with local database/object-store data. No AI API key is required.

The local services are:

- KnowFlow sign-in and workspace UI: <http://localhost:3000>
- FastAPI and OpenAPI: <http://localhost:8000/docs>
- API liveness/readiness: <http://localhost:8000/health/live> and <http://localhost:8000/health/ready>
- Identity API: `GET /api/v1/me`
- Workspace API: `GET/POST /api/v1/workspaces`, `GET /api/v1/workspaces/{id}`, and workspace member endpoints.
- Knowledge areas: `GET/POST /api/v1/workspaces/{id}/knowledge-areas`, `GET/PATCH/DELETE /api/v1/workspaces/{id}/knowledge-areas/{area_id}`. Members can read; Owners manage.
- Documents: `GET/POST /api/v1/workspaces/{id}/documents`, `GET/DELETE /api/v1/workspaces/{id}/documents/{document_id}`, and `GET /api/v1/workspaces/{id}/documents/{document_id}/content`. Owners upload/delete; Members can view/download. Originals are private MinIO objects locally; PostgreSQL stores metadata.
- PostgreSQL with pgvector: `localhost:5432`
- MinIO console: <http://localhost:9001>
- Document worker: the `worker` Compose service, using the same backend image/code as the API.
- Workspace search: `POST /api/v1/workspaces/{id}/search`, available to Owners and Members. It remains the M5 ranked retrieval API.
- Ask KnowFlow: `POST /api/v1/workspaces/{id}/ask`, available to Owners and Members. Returns best and supporting verbatim evidence, an evidence state and source/page links. It makes no generative AI call.

The authenticated web app uses a shared workspace shell with Overview, Ask KnowFlow, Knowledge areas, Documents, and Members navigation. Member-management controls are shown only to Owners; FastAPI continues to enforce each operation. The overview summarizes existing area/document/status data without a new analytics service. Document status can be refreshed from the library while processing. Source links remain protected through the Next.js-to-FastAPI streaming route.

Temporary backend/network failures are shown through generic retryable UI states; inaccessible workspace resources continue to return a not-found page. Browser-facing error messages do not include internal exception details.

M7 local frontend checks include `cd apps/web && npm test`, which runs the dependency-free Node test suite for Owner/Member UI capabilities, document status labels, and safe Ask error messages. See [the engineering guide](docs/KNOWFLOW_ENGINEERING_GUIDE.md) for the M1–M7 route structure and interaction details.

Uploads create a `PROCESS_DOCUMENT` job in the same PostgreSQL transaction as document metadata. Job states are `QUEUED`, `RUNNING`, `RETRYABLE_FAILURE`, `PERMANENT_FAILURE`, `SUCCEEDED`, and `CANCELLED`; document states are `UPLOADED`, `PROCESSING`, `READY`, `FAILED`, and `DELETING`. The worker extracts text per page, normalizes it, creates deterministic overlapping chunks, generates local embeddings and commits pages, embedded chunks, `READY`, and `SUCCEEDED` atomically. Empty/scanned or malformed PDFs fail without OCR. A deleted document's queued/running work is cancelled and derived rows are removed.

Follow worker logs with:

```sh
docker compose logs -f worker
```

Inspect job state and safe error details with:

```sh
docker compose exec db psql -U knowflow -d knowflow -c \
  "SELECT j.id, j.document_id, j.status, j.attempt_count, j.available_at, j.last_error_code, d.status AS document_status FROM processing_jobs j JOIN documents d ON d.id = j.document_id ORDER BY j.created_at DESC LIMIT 20;"
```

Owners can retry failed documents from the document list. Job attempts use the configured maximum and bounded backoff; a worker crash is recovered after the lease expires. No Redis or external queue is used.

Chunking is configurable with `KNOWFLOW_CHUNK_SIZE_CHARS` (default 1800) and `KNOWFLOW_CHUNK_OVERLAP_CHARS` (default 240). The embedding runtime uses `KNOWFLOW_EMBEDDING_MODEL=intfloat/e5-small-v2`, pinned revision `ffb93f3bd4047442299a41ebb6fa998a38507c52`, 384 dimensions, `KNOWFLOW_EMBEDDING_VERSION=v1`, CPU device, cache path `/models`, and batch size 16. E5 uses `passage: ` prefixes for stored chunks and `query: ` prefixes for searches. Model files are cached by the `model_cache` Compose volume, shared by API and worker. No provider/API key configuration exists. The model supports up to 512 tokens per input; longer inputs are truncated.

The backend pins PyTorch to 2.8.0. Docker and Linux CI install the matching `2.8.0+cpu` wheel from PyTorch's CPU-only wheel index before the other Python dependencies, so ARM64 and x86_64 Linux environments do not resolve the default CUDA-enabled PyPI build. Native macOS installs use the same pinned PyTorch version, while KnowFlow explicitly runs inference on CPU. The Docker dependency layer is based on `pyproject.toml` and `constraints-linux-cpu.txt`, and is built before application source is copied, so changing Python code does not reinstall dependencies.

### M8.2 deployment backend topology (opt-in)

Normal local Compose remains unchanged: API and worker run in separate containers, use the local Sentence Transformers provider, and the worker polls every 2 seconds. For the eventual constrained portfolio backend, `backend/Dockerfile.onnx` provides a CPU-only ONNX image with the pinned E5 artifact baked in, no PyTorch/Sentence Transformers, a non-root runtime user, and ONNX batch size 1. Configure the service with `KNOWFLOW_EMBEDDING_BACKEND=onnx`, `KNOWFLOW_EMBEDDING_BATCH_SIZE=1`, `KNOWFLOW_RUN_WORKER_IN_API=true`, and `KNOWFLOW_WORKER_POLL_INTERVAL_SECONDS=600`. The setting validator rejects enabling this topology with another backend or batch size.

When enabled, FastAPI initializes one process-cached embedding provider/session before accepting traffic and passes that same provider to its existing PostgreSQL durable worker loop. The worker processes one job at a time; ONNX inference is serialized between worker and search requests to control peak memory. After a successful upload or retry, an in-process event wakes the worker immediately; PostgreSQL remains the durable source of truth and a 10-minute polling interval is the recovery fallback. This lets an idle Neon database suspend between checks without delaying normal upload processing. Shutdown stops new claims and interrupts at processing checkpoints. An interrupted job retains its lease and is recovered by the existing expired-lease/fencing logic after restart. `/health/ready` checks PostgreSQL, the pgvector extension, provider initialization, and worker-thread liveness; it never runs an embedding. The ONNX model is part of the image, so runtime model download is not required. These settings prepare the backend image only; no cloud resources or deployment have been created.

For a native Linux Python environment, use the same CPU wheel first, then apply the committed constraint:

```bash
cd backend
python -m pip install --index-url https://download.pytorch.org/whl/cpu "torch==2.8.0+cpu"
python -m pip install -e ".[dev,local-embeddings]" --constraint constraints-linux-cpu.txt
```

On macOS, install the project normally from `backend` with `python -m pip install -e ".[dev,local-embeddings]"`; the app's configured inference device remains CPU.

For the deployment-only ONNX E5 image, 512 MiB Docker benchmark, PyTorch/ONNX vector comparison, and real PostgreSQL retrieval checks, see [the M8.1 local ONNX verification guide](docs/M8.1_LOCAL_ONNX_BENCHMARK.md).

Semantic retrieval uses pgvector cosine distance with exact scans for the small current corpus. PostgreSQL FTS uses `websearch_to_tsquery('english', ...)`, `ts_rank_cd`, and a GIN index over `to_tsvector('english', text)`. Independent top-30 lists are combined with RRF (`KNOWFLOW_RRF_K=60`) and capped at `KNOWFLOW_RETRIEVAL_TOP_K=6`; candidate limits are configurable. Results include document/chunk IDs and page ranges and only include active READY documents with vectors matching the configured model/version. Search is workspace membership protected in FastAPI. An inaccessible knowledge-area ID returns 404.

The M5 migration requeues active READY/PROCESSING documents through their existing processing jobs and sets them to UPLOADED, fencing any prior in-flight lease. The worker must finish embedding before they become READY/searchable again. Failed documents can be retried by an Owner. Changing the model/dimension/version requires an explicit re-embedding rollout; dimensions are pinned by migration and settings validation.

The model is pretrained open-source software running locally; KnowFlow does not train a model. Document text and search queries are embedded inside the API/worker containers and are not sent to an AI inference service. Search and Ask KnowFlow use no paid AI API, no generative model, and no LLM. Ask KnowFlow selects and presents source passages; it never claims to synthesize a factual answer.

M6 uses hidden/internal PostgreSQL FTS rank and pgvector cosine similarity in addition to source-text structure and answer-type evidence. `KNOWFLOW_EVIDENCE_MINIMUM_VECTOR_SIMILARITY=0.72` is a starting cosine threshold, not a confidence score. Strong evidence needs either lexical FTS support with meaningful query overlap or a sufficiently similar vector candidate plus a matching answer type such as frequency, quantity, timing, or responsible role. Evidence-quality logic has no business-domain synonym dictionary and does not treat vector rank #1 or RRF score as proof. Results from different documents remain separate, with their own page provenance; KnowFlow does not reconcile policy differences. This deterministic approach can still be uncertain for ambiguous questions and is not a general language-understanding guarantee.

For a manual retrieval/evidence check, upload both `docs/samples/KnowFlow_Sample_HR_Policies.pdf` and `docs/samples/KnowFlow_Sample_Information_Security_Policy.pdf` to the same workspace and wait until both show **Ready** (`docker compose logs -f worker`). Try **“How much annual leave do employees receive?”**, **“How much vacation time do staff get?”**, **“How many days can employees work remotely?”**, **“When must a security incident be reported?”**, **“What is the maternity leave entitlement?”**, **“How often are administrator permissions reviewed?”**, **“How often are backups performed?”**, **“When should a leaver's system access be removed?”**, **“How quickly must a security incident be reported?”**, and **“How much is the employee BYOD allowance?”**. The annual-leave and vacation questions should surface 25 working days; remote work should prefer the policy over question/reference text; unsupported maternity/BYOD questions must not promote related passages to best evidence. Security-policy evidence should preserve the cited source and page, including its daily backup, quarterly access review, departure deadline, or incident timing. When documents give different reporting timelines, KnowFlow should show their source passages separately without synthesizing a single rule. No AI API credential is needed.

M3 upload validation accepts PDFs with a valid structure, no password protection, up to 20 MiB and 250 pages. A deleted document immediately returns 404 to application requests. Storage cleanup is retried on an Owner delete request for up to 24 hours; after successful cleanup, the metadata tombstone remains for 7 days and is then purged during subsequent document/area operations.

Readiness is expected to fail until the database migrations have been applied. Copy `.env.example` to `.env`, configure WorkOS, then start Compose. The example database and object-store credentials are local development defaults only.

## Stop local services

```sh
docker compose down
```

Remove the local database and object storage volumes only when you intend to discard local data:

```sh
docker compose down --volumes
```

The model cache is also removed by `docker compose down --volumes`. Keep local data and cache with ordinary `docker compose down`.

Do not commit `.env` or provider secrets. Authentication works only after WorkOS staging credentials and redirect settings are configured.
